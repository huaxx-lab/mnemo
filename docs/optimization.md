# 优化记录与后续清单

基线 `34dd786` → 当前分支，自动测试 57 → **136 全绿**。

这份文档记的是**为什么改**，不是改了什么。每条按「现象 / 根因 / 改法」写，
因为这一轮里绝大多数问题的表象和根因都不在同一层——照着表象打补丁只会把
下一次的排查变得更难。

---

## 1. 刘海与窗口

### 1.1 展开点不动、收起后留下死区

- **现象**：展开再收起之后，刘海某些区域点不动；有时点了没反应。
- **根因**：面板的可见性与「收不收鼠标」散在二十多个赋值点（展开一处、收起一处、
  拖拽武装一处、解除一处、启动一处）。任何一条路径漏掉一个面板，输入就落进黑洞。
- **改法**：`NotchWindowPolicy.plan(...)` 作为纯函数投影出四个面板的
  `isOnScreen / acceptsMouse`，窗口层只负责幂等应用；别处一律不许再写
  `ignoresMouseEvents` 或 `orderOut`。

### 1.2 收起动画那 280ms 点击落空

- **现象**：刚收起就想再点开，打在空气上。
- **根因**：`closing` 也被算进「工作台已呈现」，锚点跟着离屏。
- **改法**：只有 `opening / open` 让位；`closing` 一开始锚点就回屏。

### 1.3 刘海下面多一条黑舌头

- **现象**：空闲时刘海正下方挂着一块黑色小舌头；有动画的状态更明显。
- **根因**：展开唇单独填了黑色底；有内容时 shell 底色又覆盖「刘海 + 唇」整块高度。
- **改法**：黑色只到刘海下沿；只有候选竖排时才把刘海、唇、列表连成同一块。
  唇本身不画东西，可点性由宿主视图一层 2% 黑保证——**透明窗口的完全透明区域
  不接收点击**，这是那次「点不动」的真正原因。

### 1.4 点复制却展开 / 点复制没反应

- **现象**：点推荐上的复制图标，工作台展开了；换个前台应用后，点复制毫无反应。
- **根因**：两件事。一是 AppKit 命中层吃掉了整条刘海带，和 SwiftUI 按钮争同一块；
  二是锚点是 `nonactivatingPanel` 且永不成为 key window，别的应用在前台时
  SwiftUI `Button` 收不到第一次点击。
- **改法**：收起态**所有**可点区域（展开唇、每条推荐行、右翼关闭）按同一份
  `NotchAnchorLayoutMetrics` 命中并执行，SwiftUI 只负责画。测试断言三类区域互不相交。

### 1.5 推荐第一行被遮住

- **现象**：多条推荐时第一行被物理刘海压住。
- **根因**：变高的列表塞进一个固定 32pt 的居中框。
- **改法**：`NotchAnchorLayoutMetrics` 同时投影 SwiftUI 尺寸、`NSPanel` frame、
  命中矩形与每一行的位置——一处算完，四处共用。

---

### 1.5 收起刘海把正在看的预览也关了

- **现象**：用户打开链接 / 文件预览后去别处对照网址，刘海自动收起时独立预览也消失。
- **根因**：`showsDetailPanel` 误把 `workspacePhase == .open` 当成详情存活条件，`closeImmediately()` 又无条件清掉 `detailItem`。
- **改法**：详情是否显示只取决于当前有详情条目且处于收纳模式；普通收起不清 `detailItem`。预览和编辑都由详情自己的关闭键明确关闭，未保存确认也只在该关闭流程发生。

## 2. 剪贴板上下文推荐

### 2.0 被动复制只判去留，Command-G 才执行推荐

- **现象**：以前复制一句普通文字也可能触发推荐，既打扰用户又把「存下来」和「拿东西」混成一条路。
- **根因**：剪贴板监听同时承担收纳、意图路由和推荐触发；任何一层误判都会直接弹 UI。
- **改法**：拆开所有权。被动复制只保留截图与普通文字；文件不自动入库；文本先用本地确定性
  规则判断，再用 LLM 兜底回答「这是不是在找东西」，只决定要不要从最近五条撤掉。模型不可用、
  格式不对或不确定时一律保留，绝不静默吞用户内容。**被动复制不再触发推荐。**
  Command-G 是唯一的快捷推荐入口：读取前台选区，不制造 Pin，不展开搜索框，直接把结果显示在刘海。

### 2.1 快捷推荐从排序器升级成有界 Agent

- **现象**：「pi agent 的网址」需要复制精确网址；「CSA-UD 是怎么运行的核心观点」却需要完整回答。
  旧路径把两者都塞进 `copyText`，结果只能拿到最多 400 字的本地摘录，甚至在英文半句中间截断。
- **根因**：交付本地对象 / 字段与生成解释是两种任务，却共用一个“挑 ID + 摘片段”输出。
- **改法**：控制器通过跨文档、图片、网页、表格、日志、代码和普通文字的成对 Few-shot，先按“用户最终要原对象 / 原值，还是新生成的解释 / 分析”返回结构化 `retrieve / answer` 意图和真实候选 ID。`retrieve` 继续走本地
  ID 白名单与逐字片段校验；`answer` 把模型选中的 Pin 只作为内部证据，不再同时显示文件卡；读取完整本地分块，按查询向量或字面分挑选
  命中窗口，再用独立 1,800-token 回答步骤生成**完整简体中文**。OpenAI 的 `finish_reason=length`
  与 Anthropic 的 `stop_reason=max_tokens` 会被识别，半成品不发布。
- **状态边界**：每次 Command-G 都重新构造 system/user 消息；没有对话历史、没有跨轮 tool state，
  只有当前 Task 的候选 ID、证据分块与回答。进程内只缓存“同请求 + 同候选 + 同路由”的最终结构化
  决策以避免重复计费，缓存内容不进入下一轮 prompt。

### 2.2 证据不是候选卡片上的短摘要

- **现象**：即使选对论文，候选 `snippet` 只有约 180 字；关键机制在长页后半段时还是看不到。
- **根因**：重排用的轻量摘要被误当成回答证据，随后又从每页开头截 2,400 字。
- **改法**：回答阶段按白名单 ID 重新从 `Library.chunks(for:)` 取分块；长分块围绕完整查询或最长
  词项截取窗口，而不是永远取页首。交付开关默认开启：按 ⌘G 时若光标位于外部可写文本输入框，回答通过 SSE 小批量写在问题选区末尾；没有输入框、开关关闭、只读 / 密码 / Mnemo 自身控件或焦点改变时，退回整段写剪贴板。只有真实写入成功才显示对应确认，失败保留回答与复制重试。答案用无描边的可滚动 Markdown 卡片显示，自绘细滑块悬浮在正文右边界且无滚动槽；不显示叉号，点击面板外自动收起。正文严格裁剪在标题下方；隐藏系统滚动槽，改用无边框自绘细滑块悬浮右边界，滚动内容不再覆盖状态图标。

### 2.3 这条路上曾经踩过的三级台阶

2.0 是终点，中间还踩过两级，都值得记下来——它们是同一个错误的不同深度：

1. **词表不认就 `return`**：意图判空后连模型都没被问到（「手册」「指南」）。
2. **交给模型路由，但没配模型时恒返回否**：「没人回答」被当成「答案是否」。
3. **最终**：不再问"这句话像不像请求"，改问"库里有没有对得上的"。

### 2.4 复制的文件也被记进了轨道

- **现象**：在访达复制一个文件，剪贴板轨道里多出一条 Pin。
- **根因**：被动监听把文件、图片、文字一视同仁。
- **改法**：被动监听只留**截图与文字**——那两类复制完就找不回；文件本来就在磁盘上，
  要收下来有两条明确的路：拖进刘海，或按 ⌃⌘P / 菜单「收纳剪贴板」。

### 2.5 判成检索的复制仍然进了最近五条

- **现象**：一句「给我发一张…的图片」既触发推荐、又占掉一条剪贴板历史。
- **根因**：先入库再异步删除，删除那一步依赖后续结论；本地判据和收纳器还各写各的。
- **改法**：`isLocalRetrievalQuery` 是收纳器与协调器**唯一**的判据，确信即不入库。

### 2.6 模型收敛到唯一一条却不自动进剪贴板

- **现象**：推荐只剩一条，仍要再点一下复制。
- **根因**：自动写回的资格里附加了「命中本地词表点名的类型」，而由模型判定为检索的
  请求本地意图本来就是空的。
- **改法**：模型可用且恰好收敛到一条、该条真的被本地检索命中（`hasLocalEvidence`）、
  非敏感字段——满足即自动准备。补位候选不具备资格，模型对补位项一样会说好。

### 2.7 显示「已复制」却粘不出来

- **现象**：对号亮了，粘贴什么都没有。
- **根因**：三层叠加。受管副本在沙盒里是 `vault/copies/<sha256>`，**没有扩展名**；
  写剪贴板只写路径字符串，永远「成功」；而路径可能指向别的应用容器，谁都读不了。
- **改法**：交出去之前按原始文件名暂存一份；写入前真读 1 字节再决定成败；
  图片另附一份 PNG 数据供只认位图的输入框。

### 2.8 同一句话再按快捷键

- **现象**：想再看一遍推荐，只能换句话说。
- **根因**：去重键命中就直接 return。
- **改法**：最终控制器结论缓存下来并重放；解释答案仍按本轮真实分块重新生成，不保存或复用
  历史 message。缓存上限 32 条，顺带修掉了原来只增不减的 key 集合。

## 3. 检索

### 3.1 搜索每次都能找到，复制推荐却经常失效

- **现象**：「我要终端使用指南」在搜索里必中，复制则毫无推荐。
- **根因**：剪贴板路径把词表猜出的类型变成**硬过滤**——「指南」判成 PDF/文件，
  这份指南若存成文字或链接，命中与候选补位都看不到它；搜索页没有这道过滤。
- **改法**：类型只作偏好。带类型召回为空时退回不限类型重来一次；候选补位先补
  同类型、再补其余，不让某一类被永久挡在模型视野之外。

### 3.2 类型词表两份，补了一边忘了另一边

- **改法**：收敛成 `ContentTypeVocabulary` 一份，剪贴板意图与查询解析共用；
  剪贴板判定出的类型直接传进检索，不让搜索端重新猜。

### 3.3 模型说第二条无关，界面照样显示

- **根因**：重排把未选中的候选又追加回结果。
- **改法**：`selectedHits` 以模型白名单为最终集合，并把模型输出分成三态：
  有效选择 / 有效空（清卡）/ 格式错误（保留本地结果并提示）；剪贴板另有
  「服务不可用」，只有这一态才降级到有本地证据的类型匹配。

### 3.4 其他

- 每次搜索全量读分块 → `ItemStore.chunks(itemIDs:)` 只取确定性过滤后的候选。
- 快捷路径没用上 Embedding → `usesEmbedding` 与 `allowsNetwork` 解耦。
- 请求套话进了查询向量 → `QueryUnderstanding.localParse` 一并剥掉。

## 4. 文件、拖拽与权限

### 4.1 从微信拖进来的文件是个空壳

- **现象**：卡片看着正常，却永远索引不了、复制不出、粘不进去。
- **根因**：存的是指向 `~/Library/Containers/com.tencent.xinWeChat/.../temp/drag/` 的
  书签。那个目录归微信所有、随时被清；而别的应用的容器受 TCC 保护，**Mnemo 连
  字节都读不到**（该条目 `indexedAt` 为空、分块 0 条，标题是模型照文件名猜的）。
- **改法**：三条路按代价从低到高——别的应用容器/缓存里的文件强制留副本；
  直接路径读不出时先用发送方的文件承诺，再退到把拖拽板上的字节自己落盘；
  都不通才失败，并明确说明需要「完全磁盘访问权限」或先存到访达。
- **实测**（`drop-trace.log`）：微信只给 `public.file-url`、`NSFilenamesPboardType`
  和几个 Qt 私有类型，**没有承诺也没有任何数据 flavor**——所以这条路只能靠授权。

### 4.2 拖入失败是静默的

- **改法**：失败时刘海边缘给警示光效；需要用户动手的失败展开工作台说明；
  每次投放把类型列表、可读性、走了哪条分支写进 `drop-trace.log`（只记结论不记内容）。

### 4.3 安全作用域没有激活

- **根因**：`FileVault.ingest` 从不 `startAccessingSecurityScopedResource`。旧实现只
  建书签、从不读内容，缺口一直没暴露；一改成必须拷贝就连属性都读不到。
- **改法**：读之前激活、用完即停。

## 5. 界面

| 问题 | 改法 |
|------|------|
| 展开面板过宽、大片留白 | 面板 600、头部 48、页签 36、内容区 236；卡片 176×128 单行，多出的高度给缩略图 |

## 6. 反复出现的四种根因

这一轮真正值钱的不是二十个补丁，而是它们共享的四个形状。后续改动照这四条走，
能省掉大部分来回。

1. **同一事实存了两份。** 类型词表、布局常数、窗口状态各有两处定义，补了一边忘了
   另一边。→ 任何被两处使用的事实，只允许有一个来源（`ContentTypeVocabulary`、
   `NotchAnchorLayoutMetrics`、`NotchWindowPolicy`）。
2. **把猜测当成硬闸门。** 类型是从一个词猜的，却被用来过滤掉答案；词表是封闭的，
   认不出就静默返回；路由没配置被当成否定。→ 猜测只能**排序与偏好**，
   不能**排除**；不确定就往下一层走，而不是就地结束。
3. **把意图当成事实。** `didAutoCopy` 在真正写成功之前就置真；写一个路径字符串
   就算复制成功。→ 状态字段描述**已经发生**的事，异步操作确认之后才发布。
4. **静默失败。** 这条链上五道闸门全是 `return`，NSLog 在打包应用里又看不到。
   → 决策链路留可读的结论日志（`drop-trace.log`），失败要有用户看得见的反馈。

## 7. 待办与技术债

**P0**

- **稳定的开发者签名。** 现在是 ad-hoc 签名，TCC 认代码签名，**每次重装完全磁盘
  访问权限都可能失效**（列表里还打着勾但实际被拒）。这也是 Keychain 反复要密码的根。
- **真实跨应用验收。** 微信/浏览器/访达的图片、PDF、文件、URL、文字拖拽；Command-G
  在浏览器、PDF 阅读器、编辑器里读取选区并分别验证文件 / 网址 / 完整中文解释；多显示器与
  无刘海降级。自动测试覆盖不到这些。

**P1**

- Keychain 仍在用已弃用的 `SecAccessCreate` / `SecAccessCopyACLList` / `SecACLSetContents`，
  编译有警告；拿到稳定签名后应换掉整套 ACL 方案。
- 大库检索：分块已改成按候选取，但仍是内存暴力余弦。定一个触发条件（条目数或
  分块数阈值）再决定是否引入索引，不要提前上 ANN。
- 图片 OCR → 上下文推荐的端到端验证：链路已接，真实截图触发尚未逐条走过。

**P2**

- 卡片密度做成紧凑 / 宽松两档由用户切换。
- 链接封面兜底：既没有 og:image 也没有站点图标时，用域名色块生成一张更像样的封面。
- 发票场景的字段抽取仍偏弱（抬头、开户行、地址是一整段，不是单个字段）。

### 2.9 微信输入框被误判成未聚焦

- **现象**：在微信输入框里选中问题按 ⌘G，回答仍进剪贴板，没有 SSE 直写。
- **根因**：微信 / Electron 把焦点、选区和写入宿主拆成不同 AX 节点；旧代码只认焦点节点的 `AXTextField / AXTextArea` role，漏掉 `AXEditableAncestor`。
- **改法**：分别解析可编辑宿主、选区载体和写入载体；原生控件走 AX 属性，微信自绘输入框在 AX 拒写时向按键时的前台进程发送定向 Unicode 键盘事件。第一段到达才折叠选区，不用 Cmd-V、不改剪贴板；CR/LF 压成普通空格，不产生 Enter / 发送事件；每段前继续验证仍在同一 editable host。AX 不提供可验证 range 时，截断半成品只标错不猜测退格。

### 2.10 Release 包体从 9 MB 增到 11 MB

- **结论**：11 MB 中主程序为 8.98 MB，原样保留的四份 ICNS 合计约 2.17 MB；不是 SSE 逻辑本身增加了 2 MB。
- **改法**：Release 组装时执行 `strip -x`，只移除主程序不参与运行的本地符号，图标和运行时资源完全不变。主程序降到约 3.7 MB，完整 App 约 6.0 MB。
